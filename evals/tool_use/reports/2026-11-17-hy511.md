# HY-511: large-result evaluation

The shipped larger internal result budget was exercised successfully on GPT and Claude.
All 15 codemode-enabled runs of the new large-result task passed, and every run made a
successful nested call returning more than 50 KB. The six direct-call control runs also
passed, using smaller pages to recover output. No runtime change was needed.

This completes the outstanding evaluation work for HY-511 locally. It does not change
Linear status, publish the results, or establish a new default.

## Setup and scope

- Base: `b47664d2512f9d1f20b84282cf6a1c97288d907a`, Wisp 0.12.0, plus the uncommitted
  additive fixture and tests accompanying this report. Existing catalog definitions and
  existing task answers are unchanged.
- Models: `openai-codex::gpt-6.1-sol`, `openai-codex::gpt-5.6-luna`,
  `anthropic::claude-sonnet-5-5`. Gemini was excluded as requested.
- Both arms use on-demand MCP discovery, text results, the same task prompt and tools,
  and the existing runner's default effort. Only codemode availability differs. This
  compares current codemode against direct calls, not an isolated old-cap/new-cap ablation.
- The task permits normal tool choice; it never instructs the model to use a script.
- The runner uses synthetic repositories, `--yes`, per-run isolation and objective
  verification. These runs do not test interactive approvals or Windows.
- Arms ran concurrently, three workers each. Latency is descriptive and may reflect
  provider load. Small samples, especially the two-run controls, do not prove equivalence.

## Fixture

`mcp-large-result-filter` asks for open EU release-gate issues whose audit title ends in
`decision=block`. Expected issue numbers: 3003, 3017 and 3033. Closed, wrong-region and
near-match-label decoys prevent a partial filter from passing.

The default page is 77,486 UTF-8 bytes; issue 3033 starts at byte 69,740. A ten-record page
is 25,826 bytes, giving the direct-call arm a valid recovery path. The entire 60-record
text-plus-structured envelope is 312,786 bytes, below 512 KiB. Tests verify these bounds,
complete pagination and rejection of plausible wrong answers.

## Large-result outcomes

Values below are off → on. Tokens include cache reads and writes using the runner's
provider-normalized accounting. Calls are top-level calls; nested calls are separate.

| Model | Passed | Mean tokens | Mean top-level calls | Mean seconds |
|---|---|---|---|---|
| GPT Sol | 2/2 → 5/5 | 241,040 → 46,303 | 18.5 → 8.2 | 65.6 → 40.9 |
| GPT Luna | 2/2 → 5/5 | 260,260 → 82,351 | 18.5 → 8.8 | 74.8 → 39.1 |
| Claude Sonnet | 2/2 → 5/5 | 587,920 → 71,615 | 17.0 → 7.8 | 38.4 → 21.1 |

The token reductions are descriptive (81%, 68%, 88%, respectively). The Welch 95%
interval excludes zero for Luna's token difference, but not for Sol or Claude. The
comparison's median token interval half-width is 220% of the earlier mean. Do not infer
precise savings from this pilot or hide the unequal sample sizes.

Trace audit: reconstructing the deterministic replies from each successful
`tool.nested.ended` call's recorded arguments confirms all 15 runs fetched results above
50 KB. Thirteen runs reached 147,204 bytes; two Luna runs used 51,652-byte pages. In Claude
rep 1, the final successful script reports all 57 eligible records and extracts all three
matches from a 147,204-byte response, returning only a short summary to the model.

Script failures were recoverable type-check errors, all before any nested calls:

| Model | Scripts | Failed scripts | Reasons | Total nested calls |
|---|---|---|---|---|
| GPT Sol | 16 | 1 | invalid-assignment | 22 |
| GPT Luna | 9 | 3 | unresolved-import | 48 |
| Claude Sonnet | 23 | 10 | 5 invalid-assignment; 5 unresolved-reference | 17 |

These failures remain a usability cost. No task failed, and there is no evidence here
of lost large results or a runtime regression. This result does not justify adding retry
caching: these failed scripts made no calls to cache.

## Budgets and infrastructure

The existing four orchestration tasks also completed:

| Model | Direct calls | Codemode available |
|---|---|---|
| GPT Sol | 12/12 | 8/8 |
| GPT Luna | 7/12 | 8/8 |
| Claude Sonnet | 12/12 | 8/8 |

The enabled arm stopped at its 600,000-token threshold after two complete rounds
(24/24); the off arm completed three (31/36). Luna's five direct-call failures were
incorrect PR identification twice and incorrect comment sums three times. There were
no infrastructure errors in the network-enabled suites. Comparing just the first two
rounds gives 20/24 off versus 24/24 on. These small samples are supporting evidence,
not a broad correctness guarantee.

Across all four network-enabled suites, known API cost was **$1.8835534**. The existing
orchestration tasks cost $0.7527084 off and $0.3506701 on.

Five repetitions per model were requested for the large task, with a $1.50 priced-run
threshold and 1,000,000 unpriced-token threshold per arm. The enabled arm completed five;
the control stopped after two complete rounds at the token threshold. The runner checks
budgets between rounds, so the threshold is not a strict cap and a round can overshoot.
Large-task known API cost: $0.5360981 off and $0.2440768 on. Codex subscription usage has
no actual USD charge reported by this runner; API-price estimates are not billed cost.

The first sandboxed orchestration attempt could not reach either provider: 36 infrastructure
errors, zero model tokens and zero recorded cost. It is retained under
`results/hy511-orchestration-python/` but excluded from capability comparisons. The subsequent
network-enabled runs are the measured runs; failures were not silently replaced.

## Reproduction

All commands use the existing environment without dependency installation:

```bash
export UV_CACHE_DIR=/tmp/wisp-uv-cache
models=openai-codex::gpt-6.1-sol,openai-codex::gpt-5.6-luna,anthropic::claude-sonnet-5-5
# Run once for each mode, using a fresh results folder each time.
uv run --no-sync python -m evals.tool_use run --models "$models" \
  --tasks mcp-large-result-filter --reps 5 --workers 3 \
  --budget-usd 1.5 --budget-tokens 1000000 --mcp-tool-exposure on_demand \
  --codemode off --results evals/tool_use/results/hy511-large-off
uv run --no-sync python -m evals.tool_use run --models "$models" \
  --tasks mcp-large-result-filter --reps 5 --workers 3 \
  --budget-usd 1.5 --budget-tokens 1000000 --mcp-tool-exposure on_demand \
  --codemode python --results evals/tool_use/results/hy511-large-python
uv run --no-sync python -m evals.tool_use compare \
  evals/tool_use/results/hy511-large-off evals/tool_use/results/hy511-large-python
```

For the existing orchestration tasks, the same run commands used `--tags orchestration`,
`--reps 3`, `--budget-usd 2`, `--budget-tokens 600000`, and results folders
`hy511-orchestration-off` / `hy511-orchestration-python-network`. Those suites were selected
before the additive task was created; to reproduce exactly now, use
`--tasks mcp-deploy-chain,mcp-failing-lint,mcp-flaky-comments,mcp-service-alerts` instead.

Sanitized baseline JSON files are under `../baselines/2026-11-17-hy511-*.json`.
Raw traces remain git-ignored under `../results/`. Run `python -m evals.tool_use report`
or `compare` against the saved baseline files to reproduce aggregate tables.
