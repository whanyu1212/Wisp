# HY-550: unified tool discovery

Unified discovery exposes a bounded catalog of eligible local and MCP tools, including
proxy-only MCP targets. Deterministic tests cover schemas, invocation/return semantics,
selection, confirmation, collisions, Unicode names and schema paging. The live evidence
shows the new capability works when requested, but does not show an efficiency advantage.

## Fresh comparison

Compared codemode off, previous codemode, and an early unified-discovery candidate on
`mcp-pick-tool-30` and `mcp-similar-servers`: two tasks, two models, three repetitions per
configuration, 36 runs. Each configuration passed all 12 objective answer verifiers.
No model used `tool_search` or `tool_describe` in these ordinary prompts. They used the
existing MCP discovery tools. The additional definitions increased mean token usage on
these small tasks; lower outer-call counts are not claimed as an efficiency gain.

| Model | Off: mean tokens | Previous: mean tokens | Candidate: mean tokens | Passes per configuration |
|---|---:|---:|---:|---:|
| GPT-5.6 Luna | 11,985 | 14,157 | 15,622 | 6/6 |
| Claude Sonnet 5.5 | 18,876 | 22,785 | 25,470 | 6/6 |

Tokens include cache reads/writes without double-counting GPT cached input. This is a small
synthetic comparison, not proof of equivalent reliability. The candidate rows refer to a
frozen earlier snapshot: subsequent fixes added Unicode search, proxy-target metadata,
custom-name collision handling and policy-aware inspection counts. Those fixes have focused
regressions and the final capability probe below; the comparison was not rerun or relabelled
as final-source evidence. In particular, the early candidate did not catalog the hyphenated
`inventory-30` targets, which remained reachable through existing MCP discovery.

## Explicit capability probe

`unified-tool-discovery` asks for the new catalog, local `read` metadata, an MCP reorder-policy
contract, a fixture read and an objective answer. Both models passed all three automated
task checks with zero tool errors. All six used `tool_search` and `tool_describe`, read the
fixture, and invoked the MCP target successfully through the existing proxy.

Trace inspection gives a narrower instruction-compliance result: **4/6** described both
the local and MCP tool through `tool_describe`. GPT did so in all three runs; Claude did so
once, used legacy `mcp_describe` for the MCP contract once, and skipped describing `read`
once. The automated verifier checks the correct answer and use of `tool_describe`, not
every requested discovery step. These distinctions are retained; no failed attempt was
silently rerun. This explicitly instructed probe does not measure spontaneous adoption.

## Verification and boundaries

- Broad coding/MCP/codemode/docs/repository run: 1,291 passed, 14 localhost socket/OAuth
  failures under the sandbox. Both affected files passed all 34 tests outside the sandbox.
- After review fixes: 274 focused codemode, discovery, MCP, overflow, stats and guide tests
  passed. Final discovery integration including fresh/forked subagents: 14 passed.
- Ruff formatting/lint, configured mypy, protocol-schema check and docs build passed.
- Independent read-only review found collision, Unicode and inspection-count issues, now
  fixed and covered; no remaining actionable findings.
- Scoped complexity review completed; changed catalog branches were inspected. Duplication
  findings were outside changed code. Coverage tooling unavailable; no installation or mutation
  testing. Full repository/CI and browser layout checks were not run for this local slice.
- Fresh subagents retain their existing tool set; forks retain parent schemas/catalog and
  still execute through the nested read-only policy. Discovery does not grant permission.
- Responses are valid JSON within 16 KiB and the tool-output budget. Large schema trees can
  be traversed by JSON Pointer; oversized indivisible values are explicitly omitted.
- Existing MCP discovery remains compatible. No availability-default, mutation, model-helper,
  wire/event or session-format changes. Automatic codemode runs receive two additional tool
  definitions; their measured overhead is a rollout consideration, not hidden by unchanged
  setting defaults.
